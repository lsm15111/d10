# CI/CD, IAM, secrets and network security for the 믿집 platform (AWS Seoul, one EC2 + RDS)

Research date: 2026-10-29. Scope: GitHub Actions → AWS OIDC, ECR, SSM-based deploys, arm64 builds, secrets, VPC/SG/IMDS, edge protection, supply chain/app security, IaC and account hygiene.
Method note: ~75 distinct URLs were consulted (fetched pages plus search-result pages). The shared web-search budget ran out partway through, so the last third of the work used direct fetches of known documentation URLs only. Korean-language engineering blogs on the exact GitHub Actions + ECR + SSM pattern could not be found before the budget ran out (see Gaps).

Overall verdict (synthesis, details below): the proposed design (OIDC → ECR → SSM Run Command → `docker compose pull && up -d`, secrets in Parameter Store, only 80/443 open, RDS in private subnets, no NAT) matches current AWS/GitHub guidance and is cheap. The main fixes and additions are: (1) write the OIDC trust policy for GitHub's **immutable-ID `sub` format**, because a repo created now gets that format by default; (2) don't give the CI role `AWS-RunShellScript`. Give it a **custom SSM document that only accepts an image tag**; (3) don't rely on `aws ssm wait command-executed`, which gives up after about 100 s; (4) **pin every action to a commit SHA**, after the tj-actions (2025) and trivy-action (March 2026) tag-rewrite attacks; (5) decide on a public or private repo with the trade-offs in mind. A public repo gets free arm64 4-vCPU runners, CodeQL, secret scanning, push protection and required reviewers. On a Free plan a private repo gets none of the security features and no environment protections; (6) set IMDSv2 and EBS encryption as account defaults before launching anything; (7) WAF can't attach to EC2. If edge filtering is wanted, the new **CloudFront flat-rate Free plan ($0, includes WAF + rate limiting + DDoS)** or Cloudflare is the way, not an ALB.

## 1. GitHub Actions → AWS OIDC best practices in 2026 (trust policy, audience, least privilege, pitfalls)

### Takeaway
Use one OIDC provider and one or two deploy roles. Each trust policy should pin `aud = sts.amazonaws.com` and an exact `sub` with `StringEquals`. Because the 믿집 repo will be created after 2026‑07‑15, its `sub` will use the **immutable `OWNER@ID/REPO@ID` format** by default. Bind the role to a GitHub environment (`:environment:production`) if the plan supports environments for the repo, otherwise to `:ref:refs/heads/main`. Scope permissions to the specific ECR repositories and to one instance ARN plus one custom SSM document.

### Cited Findings
- Provider URL is `https://token.actions.githubusercontent.com`; the audience is `sts.amazonaws.com` when using the official action; the job needs `permissions: id-token: write` (plus `contents: read` for checkout), and this permission does not grant write access to resources. — [GitHub Docs: OIDC in AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)
- Subject formats: branch `repo:ORG/REPO:ref:refs/heads/BRANCH`; environment `repo:ORG/REPO:environment:ENV`; pull request `repo:ORG/REPO:pull_request` (only when the job references no environment); tag `repo:ORG/REPO:ref:refs/tags/TAG`. — [GitHub Docs: OIDC reference](https://docs.github.com/en/actions/reference/security/oidc); [GitHub Docs: OIDC in AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)
- **Immutable subject claims:** repositories created after **July 15, 2026** (and repos renamed/transferred after that date, or that opt in) emit `repo:OWNER@OWNER-ID/REPO@REPO-ID:...`, e.g. `repo:octo-org@123456/octo-repo@456789:ref:refs/heads/octo-branch`. Older repos keep the legacy format unless they opt in through the OIDC settings UI/REST API. Not available on GHES. — [GitHub Docs: OIDC reference](https://docs.github.com/en/actions/reference/security/oidc); [GitHub Docs: OIDC in AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)
- The IDs exist to block slug-reuse attacks: if an org name is released and re-registered, slug-based trust policies would match the new owner. A practitioner observed the switch in their org between July 10 and 17, 2026. Advice from the same post: pin the numeric org ID rather than wildcarding it, put wildcards only under `StringLike` (under `StringEquals` they're compared literally and never match), and use CloudTrail's failed `AssumeRoleWithWebIdentity` event to see the exact rejected subject (STS is regional, so look in the right region). — [AWS Builder Center: GitHub OIDC changes that can break AWS deployments](https://builder.aws.com/content/3Gkby3FG8juxMqEXkwPzk5hsPz3/github-oidc-changes-that-can-break-aws-deployments/); [DEV (AWS Builders): GitHub changed its OIDC subject claims](https://dev.to/aws-builders/github-changed-its-oidc-subject-claims-and-broke-my-aws-deploys-for-new-repos-2cfp)
- `aws-actions/configure-aws-credentials` is at **v6** (examples pin v6.3.0) and has used immutable releases since 5.0.0. Defaults are `audience: sts.amazonaws.com`, `role-session-name: GitHubActions` (setting it to the run ID helps with CloudTrail correlation) and `role-duration-seconds: 3600` (range 900–43200). Thumbprints are no longer needed and are ignored if given. Avoid `ForAllValues:` in Allow statements. Legacy-format trust policies fail against immutable-ID repos with `Not authorized to perform sts:AssumeRoleWithWebIdentity`. Be careful with `pull_request_target`. — [aws-actions/configure-aws-credentials README](https://github.com/aws-actions/configure-aws-credentials)
- **IAM itself enforces a `sub` condition:** when GitHub's provider is the trusted principal, IAM rejects trust-policy create/update if `token.actions.githubusercontent.com:sub` is missing or is only `*`/`?`/null. AWS also "strongly recommends" environment protection rules (deployment branches/tags) when environments are used in OIDC policies. — [AWS IAM User Guide: Create a role for OIDC federation](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-idp_oidc.html)
- Without a `sub` condition, any external repository can assume the role, and GitHub code search finds public workflows with such trust policies. Broad wildcards such as `repo:PaloAltoNetworks*/repo*` can be matched by a look-alike org (2023 research, still relevant). — [Palo Alto Networks: OpenID Connect – Let's Talk Security (2023-09-12)](https://www.paloaltonetworks.com/blog/cloud-security/openid-connect-oidc-security/); a similar informal study found external repos assuming roles: [Tinder Tech: Identifying vulnerabilities in GitHub Actions & AWS OIDC configurations](https://lifeattinder.com/blog/identifying-vulnerabilities-in-github-actions-aws-oidc-configurations)
- Custom subject templates (`include_claim_keys`, e.g. `["repo","context","job_workflow_ref"]`) can bind the subject to a specific (reusable) workflow file. Add the matching cloud-side condition *before* changing the template or new tokens get rejected. Dependabot jobs use `event_name: dynamic`. — [GitHub Docs: OIDC reference](https://docs.github.com/en/actions/reference/security/oidc)
- Minimum ECR push policy: `ecr:CompleteLayerUpload, UploadLayerPart, InitiateLayerUpload, BatchCheckLayerAvailability, PutImage, BatchGetImage` on the repository ARN, plus `ecr:GetAuthorizationToken` on `*`. — [Amazon ECR User Guide: IAM permissions for pushing an image](https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-push-iam.html)
- Run Command access can be limited to managed nodes by ARN or tag (`ssm:resourceTag/...`). The AWS examples allow `ssm:SendCommand` on the **document** resource and the **instance** resource as separate statements, plus `ssm:ListCommands/ListCommandInvocations/GetDocument`. If any global condition key is used on `SendCommand`, `aws:ViaAWSService: true` must also be handled. — [AWS SSM User Guide: Setting up Run Command](https://docs.aws.amazon.com/systems-manager/latest/userguide/run-command-setting-up.html)
- A Japanese 2024 tech-blog example of this pattern trusted `repo:xxx:*` and allowed `ssm:SendCommand` on `instance/*` with `AWS-RunShellScript`, which is broader than necessary. — [Zenn (レスキューナウ, 2024-08-09)](https://zenn.dev/rescuenow/articles/9facd2d4be02a1)

### Inferences
- **Recommended deploy-role trust policy** (fill in IDs from `GET /repos/{owner}/{repo}` → `owner.id`, `id`, or read the `sub` from a debug run):
  ```json
  {"Effect":"Allow",
   "Principal":{"Federated":"arn:aws:iam::<ACCT>:oidc-provider/token.actions.githubusercontent.com"},
   "Action":"sts:AssumeRoleWithWebIdentity",
   "Condition":{"StringEquals":{
     "token.actions.githubusercontent.com:aud":"sts.amazonaws.com",
     "token.actions.githubusercontent.com:sub":"repo:<ORG>@<ORG_ID>/<REPO>@<REPO_ID>:environment:production"}}}
  ```
  If the repo is private on GitHub Free, where environments aren't available for private repos (see Q5), use `...:ref:refs/heads/main` instead. Don't use `StringLike` with `*` for the deploy role. If you do need a wildcard (for example a read-only role for PRs), use `StringLike` and still pin the numeric IDs.
- **Role split:** CI (ruff, pytest with service containers, typecheck, next build) needs **no AWS role at all**, so never request `id-token: write` in PR workflows. A single `mitjip-gha-deploy` role bound to `environment:production`/`main`, with (a) ECR push on `arn:aws:ecr:ap-northeast-2:<ACCT>:repository/mitjip/*` and (b) `ssm:SendCommand` on `arn:aws:ec2:ap-northeast-2:<ACCT>:instance/i-<id>` plus `arn:aws:ssm:ap-northeast-2:<ACCT>:document/mitjip-deploy`, and (c) `ssm:GetCommandInvocation`/`ListCommandInvocations`, is enough. Two roles (push vs deploy) add only a little safety at this scale.
- **Do not allow `AWS-RunShellScript`** for the CI role. That would let anyone who can run the deploy workflow execute arbitrary root commands on the production host. A custom document with one `ImageTag` parameter is safer (see Q3).
- Set `role-session-name: gha-${{ github.run_id }}` and `role-duration-seconds: 900–1800` so CloudTrail entries map to runs and tokens are short-lived.

### Gaps
- Which additional GitHub claims (beyond `aud`/`sub`) AWS IAM exposes as condition keys in 2026 was not verified, so the recommendation relies on `sub` only.
- The exact opt-in API path for immutable claims on pre-July-2026 repos wasn't fetched. It doesn't matter here, because a new repo gets the new format by default.

## 2. ECR: immutable tags, lifecycle policies, basic vs enhanced scanning, pulling via instance profile, costs

### Takeaway
Create one private repo per image (e.g. `mitjip/web`, `mitjip/api`; the arq worker can reuse the api image). Make tags **IMMUTABLE**, using `IMMUTABLE_WITH_EXCLUSION` only if a mutable `buildcache` or `latest` tag is needed. Tag images by git SHA. Add a lifecycle policy (expire untagged after 1 day, keep the last ~15 tagged). Turn on free basic scan-on-push. On the host, use `amazon-ecr-credential-helper` with the instance role. Expected ECR cost is well under $1/month. Enhanced (Inspector) scanning costs about $0.09 per pushed image plus $0.01 per rescan.

### Cited Findings
- Private storage costs $0.10/GB-month, and new customers get 500 MB/month free for one year. Transfer from ECR to EC2 **in the same Region is free**. — [Amazon ECR pricing](https://aws.amazon.com/ecr/pricing/)
- ECR bills the compressed size of *unique* layers, not the number of images pushed (third-party). — [CloudBurn: Amazon ECR pricing](https://cloudburn.io/blog/amazon-ecr-pricing)
- Since July 23, 2025, ECR supports **exceptions to tag immutability**, e.g. keep release tags immutable while `latest` stays mutable. The modes are `MUTABLE | IMMUTABLE | MUTABLE_WITH_EXCLUSION | IMMUTABLE_WITH_EXCLUSION`, with 1–5 wildcard filters of up to 128 characters. — [AWS What's New 2025-07](https://aws.amazon.com/about-aws/whats-new/2025/07/amazon-ecr-exceptions-tag-immutability/); [AWS CLI put-image-tag-mutability](https://docs.aws.amazon.com/cli/latest/reference/ecr/put-image-tag-mutability.html); [CloudFormation AWS::ECR::Repository](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-ecr-repository.md)
- Lifecycle policies act **within 24 hours** of an image meeting the criteria, and AWS recommends running a preview first. The `countType` options are `imageCountMoreThan`, `sinceImagePushed`, `sinceImagePulled` (new) and `sinceImageTransitioned` (for the archive storage class). `tagPatternList`/`tagPrefixList` work only with `tagStatus: tagged`, with at most 4 wildcards per pattern. An image referenced by a manifest list can't expire until the list is deleted. Lifecycle actions are logged to CloudTrail. — [Amazon ECR User Guide: Lifecycle policies](https://docs.aws.amazon.com/AmazonECR/latest/userguide/LifecyclePolicies.html); [ECR lifecycle policy examples](https://docs.aws.eu/AmazonECR/latest/userguide/lifecycle_policy_examples.html)
- **Basic scanning** now uses "AWS native technology" (more than 50 feeds including NVD and MITRE), covers OS packages, runs scan-on-push via repository filters and allows one scan per image per 24 h. It is free and billed through ECR. — [Amazon ECR User Guide: basic scanning](https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-scanning-basic.html); [Inspector: scanning ECR](https://docs.aws.amazon.com/inspector/latest/user/scanning-ecr.md)
- **Enhanced scanning** is billed through Amazon Inspector: about $0.09 per image for the initial scan on push and $0.01 per continuous rescan. Inspector CI/CD scanning costs $0.03 per image, and new accounts get a 15-day free trial (US East examples). — [Amazon Inspector pricing](https://aws.amazon.com/inspector/pricing/)
- `amazon-ecr-credential-helper`: install with `sudo dnf install -y amazon-ecr-credential-helper` on AL2023 and set `"credsStore": "ecr-login"` (or per-registry `credHelpers`) in `/root/.docker/config.json`. It uses the standard AWS credential chain including IAM roles for EC2, needs no `docker login`, and caches tokens in `~/.ecr`. — [awslabs/amazon-ecr-credential-helper](https://github.com/awslabs/amazon-ecr-credential-helper)
- An AWS Prescriptive Guidance pattern (Korean edition) for GitHub Actions → ECR via OIDC scopes the GitHub role with an ECR-specific policy and ships a sample lifecycle policy. — [AWS 권장 가이드: GitHub Actions 및 Terraform으로 Docker 이미지를 ECR에 푸시](https://docs.aws.amazon.com/ko_kr/prescriptive-guidance/latest/patterns/build-and-push-docker-images-to-amazon-ecr-using-github-actions-and-terraform.html)

### Inferences
- **Suggested lifecycle policy:** rule 1 (priority 1): `tagStatus: untagged`, `sinceImagePushed` 1 day → expire. Rule 2 (priority 2): `tagStatus: any`, `imageCountMoreThan: 15` → expire. Fifteen SHA tags give plenty of rollback depth, and with shared base layers storage likely stays at 1–5 GB (≈ $0.10–0.50/month).
- If you use a registry build cache (`ref=…:buildcache`) in the same repo, the repo must be `IMMUTABLE_WITH_EXCLUSION` with `buildcache*` excluded, or the cache should live in a separate mutable repo such as `mitjip/cache`.
- Instance-role ECR permissions: the AWS-managed `AmazonEC2ContainerRegistryReadOnly` policy, or a scoped policy (`ecr:GetAuthorizationToken` on `*`, plus `BatchGetImage`/`GetDownloadUrlForLayer`/`BatchCheckLayerAvailability` on `mitjip/*`). The pull-permission page itself wasn't fetched.
- Enhanced scanning is optional at this scale. About 60 image pushes a month ≈ $5.40 plus rescans. A free Trivy step in CI (pinned by SHA, see Q8) together with basic scanning covers most of the value. Inspector also covers language packages (pip/npm), which basic scanning doesn't, so it may be worth it during the 15-day trial or just before a demo.

### Gaps
- Inspector prices for Seoul specifically weren't shown (US East examples only).
- The official ECR page on pull permissions (instance role) wasn't fetched.

## 3. Deployment pattern: SSM Run Command vs SSH vs CodeDeploy vs Kamal; waiting for results; rollback; migrations

### Takeaway
SSM Run Command is the right choice for this stack. It's free on EC2, the agent is preinstalled on AL2023/Ubuntu, it needs no inbound port, and every call is in CloudTrail. Harden it with a **custom Command document** (validated `ImageTag` parameter, `interpolationType: ENV_VAR`) and a **custom polling loop**, because the built-in waiter gives up after about 100 s. Send full output to CloudWatch Logs, since the API returns only the first 24,000 characters of stdout. Roll back by redeploying the previous SHA tag. Run Alembic as a one-shot container **before** `up -d`, and keep migrations backward-compatible (expand/contract) so an image rollback never needs a DB downgrade.

### Cited Findings
- Run Command and Session Manager have **no additional charge on EC2**. Hybrid/multicloud nodes have been billed since Sept 30, 2026 ($0.002 per invocation, $0.05 per session), which doesn't apply to EC2. — [AWS Systems Manager pricing](https://aws.amazon.com/systems-manager/pricing/)
- SSM Agent is preinstalled on Amazon Linux 2023 and Ubuntu Server 22.04/24.04 AMIs (the preinstalled version may not be the latest). — [AWS SSM: AMIs with SSM Agent preinstalled](https://docs.aws.amazon.com/systems-manager/latest/userguide/ami-preinstalled-agent.html)
- The instance profile needs `AmazonSSMManagedInstanceCore` (plus ECR read for pulls), and CloudTrail logs every invocation with the full command text (from the article's search snippet; the full article returned 403 when fetched). — [AWS in Plain English: Deploy Docker to EC2 with GitHub Actions and SSM](https://aws.plainenglish.io/how-to-deploy-docker-to-ec2-securely-with-github-actions-and-aws-ssm-stop-using-ssh-forever-dbec2ef9585a)
- `aws ssm wait command-executed` polls `GetCommandInvocation` **every 5 s, up to 20 times** (≈100 s), then exits 255. In the waiter definition, `Success` means success, `Cancelled/TimedOut/Failed/Cancelling` mean immediate failure, and `Pending/InProgress/Delayed`/`InvocationDoesNotExist` mean retry. — [AWS CLI: ssm wait command-executed](https://docs.aws.amazon.com/cli/latest/reference/ssm/wait/command-executed.html); [botocore SSM waiters-2.json](https://raw.githubusercontent.com/boto/botocore/develop/botocore/data/ssm/2014-11-06/waiters-2.json)
- `get-command-invocation` returns only the **first 24,000 characters of stdout and 8,000 of stderr**. Full output requires an S3 bucket (`StandardOutputUrl`) or CloudWatch output (`CloudWatchOutputEnabled`, default group `aws/ssm/<DocumentName>`). `ResponseCode -1` means the command never started. — [AWS CLI: ssm get-command-invocation](https://docs.aws.amazon.com/cli/latest/reference/ssm/get-command-invocation.html)
- Run Command can stream output to CloudWatch Logs and publish status changes to EventBridge. — [AWS SSM: Setting up Run Command](https://docs.aws.amazon.com/systems-manager/latest/userguide/run-command-setting-up.html)
- SSM document parameters support `allowedPattern` (a regex validated both by the API and on the agent), `allowedValues`, `minChars/maxChars`, and **`interpolationType: ENV_VAR`**, which exposes the value as `SSM_<name>` and "helps prevent command injection by treating parameter values as literal strings". Command documents support only String/StringList, and schema 2.2 is recommended. — [AWS SSM: Document data elements and parameters](https://docs.aws.amazon.com/systems-manager/latest/userguide/documents-syntax-data-elements-parameters.html)
- A real-world example sent the command and exited **without waiting or checking status**, so a failed deploy would still show a green run. — [Zenn (レスキューナウ)](https://zenn.dev/rescuenow/articles/9facd2d4be02a1)
- Kamal (v2.12.0) is "Capistrano for containers": it deploys over **SSH**, auto-provisions Docker, and does zero-downtime and rolling restarts. `kamal rollback <version>` restarts an older container without pulling anything, but old containers are pruned after 3 days by default. — [Kamal](https://kamal-deploy.org/); [Kamal: rollback](https://kamal-deploy.org/docs/commands/rollback/)
- Session Manager port forwarding to a remote host (`AWS-StartPortForwardingSessionToRemoteHost`, agent ≥ 3.1.1374.0) gives developers access to RDS without SSH or a bastion. Session logging isn't available for port-forwarding/SSH sessions. — [AWS SSM: Start a session](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-sessions-start.html)
- The CodeDeploy pricing page fetched didn't list EC2 rates. — [AWS CodeDeploy pricing](https://aws.amazon.com/codedeploy/pricing/)

### Inferences
- **Custom document `mitjip-deploy`** (schema 2.2): parameter `ImageTag` (`type: String`, `allowedPattern: "^[0-9a-f]{40}$"`, `interpolationType: ENV_VAR`). The single step runs `/opt/mitjip/deploy.sh "$SSM_ImageTag"`, and that script is root-owned and lives on the host, not in the document. The script should:
  1. `aws ssm get-parameters-by-path` → write the secret files (Q5);
  2. `IMAGE_TAG=$tag docker compose pull`;
  3. `docker compose run --rm migrate alembic upgrade head`, aborting on a non-zero exit;
  4. `docker compose up -d --remove-orphans`;
  5. run a health check (curl `https://localhost/healthz` through Caddy, or the api container's health endpoint), and if it fails, re-run `up -d` with the tag stored in `/opt/mitjip/last_good_tag`;
  6. on success, write the new tag to `last_good_tag` and `docker image prune` old images.
- **Workflow side:** `CMD_ID=$(aws ssm send-command --document-name mitjip-deploy --instance-ids i-… --parameters ImageTag=$GITHUB_SHA --cloud-watch-output-config CloudWatchOutputEnabled=true --query Command.CommandId --output text)`. Then poll `get-command-invocation` every 10 s for up to ~10 min until the status is terminal, print `StandardOutputContent`, and `exit 1` unless the status is `Success`. Add a GitHub `concurrency: production-deploy` group so two deploys never overlap.
- **Rollback:** a `workflow_dispatch` input `image_tag` that calls the same document with an older SHA. This works because ECR keeps the last ~15 tags (Q2). It needs no SSH and no rebuild.
- **Migrations:** with a single host there's a short window where the old app runs against the new schema, and rolled-back images run against an already-migrated schema. Keep every migration additive (add nullable column → backfill → switch code → drop in a later release), and take a manual RDS snapshot before destructive migrations. `docker compose up -d` recreates containers, so expect a few seconds of 502s from Caddy. That's acceptable for tens of users. Blue/green on one host isn't worth the complexity.
- **Comparison:** SSH needs port 22 open to GitHub's large IP ranges or a self-hosted runner, plus a long-lived private key stored in GitHub secrets, so it's worse on every axis. CodeDeploy adds an agent, an appspec and S3 bundles for no benefit over SSM at one instance. Kamal is good but SSH-based, so it conflicts with the "no SSH" goal.

- No fetched source (the search budget was exhausted) on Alembic expand/contract patterns specifically. The migration guidance above is inference.
- CodeDeploy's EC2 price could not be confirmed from the fetched page.

## 4. Building arm64 images: hosted arm64 runners (availability/pricing), QEMU vs native, build cache, multi-arch

### Takeaway
No QEMU needed. Since **2026‑01‑29**, `ubuntu-24.04-arm` standard runners work in **private** repos (2 vCPU/8 GB, $0.005/min, drawn from the plan's included compute). In public repos they're free with 4 vCPU/16 GB. Build `linux/arm64` only (no multi-arch manifest needed for a t4g target), with `docker/build-push-action` and `cache-from/to: type=gha,mode=max,scope=<image>`.

### Cited Findings
- Changelog of 2026‑01‑29: Linux and Windows arm64 standard runners (`ubuntu-24.04-arm`, `ubuntu-22.04-arm`, `windows-11-arm`) are available in private repositories with **2 vCPUs** (4 in public repos), and usage counts toward the plan's included minutes. — [GitHub Changelog 2026-01-29](https://github.blog/changelog/2026-01-29-arm64-standard-runners-are-now-available-in-private-repositories)
- Runner reference: the private-repo table lists `ubuntu-24.04-arm`, `ubuntu-22.04-arm`, `ubuntu-26.04-arm` at 2 CPU / 8 GB / 14 GB SSD; public repos get 4 CPU / 16 GB / 14 GB. — [GitHub Docs: GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)
- Earlier history: arm64 for public repos went to public preview in Jan 2025 and GA in Aug 2025, and at that time didn't work in private repos. — [GitHub Changelog 2025-01-16](https://github.blog/changelog/2025-01-16-linux-arm64-hosted-runners-now-available-for-free-in-public-repositories-public-preview/); [GitHub Changelog 2025-08-07](https://github.blog/changelog/2025-08-07-arm64-hosted-runners-for-public-repositories-are-now-generally-available/)
- Prices per minute: Linux 2-core x64 $0.006, **Linux 2-core arm64 $0.005**; larger arm64 Linux runners up to $0.098 (64-core). Larger runners aren't free in public repos. — [GitHub Docs: Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)
- Included compute is now expressed **in dollars**: Free $12/month, Pro $18, Team $18. Artifact storage is 500 MB / 1 GB / 2 GB, and cache is 10 GB per repo. Standard hosted runners in public repos are free and don't consume the allowance. — [GitHub Docs: GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- On 2026‑01‑01 hosted-runner prices dropped by up to 39% (larger machines saw bigger cuts). The planned $0.002/min self-hosted platform fee (originally March 1, 2026) was **postponed**, and Actions remain free for public repos. — [GitHub: 2026 pricing changes for GitHub Actions](https://github.com/resources/insights/2026-pricing-changes-for-github-actions); [GitHub Changelog 2025-12-16](https://github.blog/changelog/2025-12-16-coming-soon-simpler-pricing-and-a-better-experience-for-github-actions/); conflicting older reports that the fee started March 1: [DOU](https://dou.ua/forums/topic/57024/), [IT Brief](https://itbrief.co.uk/story/github-cuts-actions-runner-prices-adds-new-usage-fee)
- Docker docs: building several platforms on one runner "can significantly extend build times". Docker recommends splitting per-platform builds across native runners (its reusable workflows map Linux Arm to `ubuntu-24.04-arm`), and QEMU via `docker/setup-qemu-action` is the fallback. — [Docker Docs: Multi-platform image with GitHub Actions](https://docs.docker.com/build/ci/github-actions/multi-platform/)
- GHA cache backend: with `build-push-action`, URL and token are populated automatically. Set a **unique `scope` per image** (the default `buildkit` scope makes images overwrite each other). Caches are branch-scoped (current/base/default), the gha API can throttle ("maximum timeout reached"), there's a 10-minute default timeout, and `ignore-error=false` by default. — [Docker Docs: GitHub Actions cache backend](https://docs.docker.com/build/cache/backends/gha/)
- GitHub cache: 10 GB per repo by default (more can be paid for), entries unused for 7 days are evicted, oldest-first eviction at the limit, and `pull_request_target`/`workflow_run` get read-only access to default-branch caches. — [GitHub Docs: Dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)
- Registry cache in ECR: `cache-to: type=registry,mode=max,image-manifest=true,oci-mediatypes=true,ref=<repo>:cache` (third-party; not confirmed against official AWS docs). The inline cache supports only `mode=min`. — [Medium: Optimizing Docker builds with GitHub Actions caching](https://medium.com/@thomasvjoseph/optimizing-docker-builds-with-github-actions-caching-5506e15a079c); [DEPT Engineering: Speed up Docker builds in GitHub Actions](https://engineering.deptagency.com/how-to-speed-up-docker-builds-in-github-actions)

### Inferences
- Example cost: two images at ~6–8 min each on a 2-core arm runner ≈ $0.06–0.08 per deploy. One hundred deploys plus CI jobs fits inside the $12 Free allowance in most months. A public repo makes it all free and twice as fast (4 vCPU).
- Run CI test jobs (pytest with Postgres/Redis service containers, `next build`) on `ubuntu-24.04-arm` as well, so the tests use the same CPU architecture as production. Service containers need arm64 images, which official `postgres:17` and `redis` provide (not verified per image tag).
- `type=gha` is the simplest cache. Move to an ECR registry cache only if gha throttling or the 10 GB limit becomes a problem.
- Developers on Windows x86 laptops keep building amd64 locally with compose. Only CI produces arm64 images.

## 5. Secrets: Parameter Store vs Secrets Manager, KMS, getting secrets into Compose, GitHub environments and reviewers

### Takeaway
Use **Parameter Store standard-tier SecureString** (free) under `/mitjip/prod/*`. Use Secrets Manager only for the RDS-managed master password ($0.40/month). The host's deploy script (instance role) fetches the parameters at deploy time and writes root-only files mounted as Compose `secrets:`. GitHub stores **no AWS or app secrets**, only the role ARN as a variable. Required reviewers on environments work only in public repos on Free/Pro/Team. On Free, private repos don't get environments' branch rules or secrets either.

### Cited Findings
- Parameter Store: standard parameters cost nothing to store, and standard-throughput API calls are free. Advanced parameters cost $0.05 per parameter per month plus $0.05 per 10,000 API interactions. Enabling **higher throughput** makes even standard-parameter calls cost $0.05 per 10,000, and one Get returning 10 parameters counts as 10 interactions. — [AWS Systems Manager pricing](https://aws.amazon.com/systems-manager/pricing/)
- Tiers: standard allows 10,000 parameters per region at 4 KB each; advanced allows 100,000 at 8 KB, plus parameter policies. You can upgrade a parameter but never downgrade it. — [AWS SSM: Managing parameter tiers](https://docs.aws.amazon.com/systems-manager/latest/userguide/parameter-store-advanced-parameters.html)
- SecureString uses KMS symmetric keys. The default is the AWS-managed `aws/ssm` key, which you can't write access policies for. A customer-managed key allows key-policy and encryption-context (`kms:EncryptionContext:PARAMETER_ARN`) restrictions. Standard parameters are encrypted directly; advanced ones use envelope encryption. Decrypting needs `kms:Decrypt` with `--with-decryption`. SecureString parameters can't be referenced from SSM document parameters. — [AWS SSM: KMS encryption for SecureString](https://docs.aws.amazon.com/systems-manager/latest/userguide/secure-string-parameter-kms-encryption.html); [AWS SSM: document parameters](https://docs.aws.amazon.com/systems-manager/latest/userguide/documents-syntax-data-elements-parameters.html)
- Secrets Manager costs $0.40 per secret per month (hourly prorated) plus $0.05 per 10,000 API calls. Since July 2025 new accounts get up to $200 in Free Tier credits that also apply to it. — [AWS Secrets Manager pricing](https://aws.amazon.com/secrets-manager/pricing/)
- An RDS-managed master password is stored in Secrets Manager at normal charges and is deleted with the instance. Default rotation is every 7 days (rotation detail from a third-party source). — [Amazon RDS: Password management with Secrets Manager](https://docs.aws.amazon.com/us_us/AmazonRDS/latest/UserGuide/rds-secrets-manager.html); [CloudBurn: Secrets Manager pricing](https://cloudburn.io/blog/aws-secrets-manager-pricing)
- Compose `secrets:` bind-mount files at `/run/secrets/<name>`, granted per service. Docker prefers them over environment variables because env vars "are often available to all processes" and "can also be printed in logs". Linux containers only. — [Docker Docs: Use secrets in Compose](https://docs.docker.com/compose/how-tos/use-secrets/)
- GitHub environments on **Free, Pro and Team**: required reviewers and wait timers are **public repos only**. Deployment branch rules and environment secrets/variables work in private repos only on Pro/Team. Up to 6 reviewers, with an option to block self-review. — [GitHub Docs: Deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)
- Next.js's React2Shell advisory told anyone whose app was online and unpatched as of Dec 4, 2025 to **rotate all secrets**, which shows why secrets must be easy to rotate. — [Next.js: CVE-2025-66478](https://nextjs.org/blog/CVE-2025-66478)

### Inferences
- **Parameters:** `/mitjip/prod/db_app_password`, `session_secret` (if used for signing), `openai_api_key`, `turnstile_secret`, `ses_from` (String) and so on, all standard SecureString with `aws/ssm`. A customer-managed KMS key adds a monthly fee (KMS pricing not fetched) and only matters if you want encryption-context-scoped decrypt.
- **Instance role:** `ssm:GetParametersByPath`/`GetParameter` on `arn:aws:ssm:ap-northeast-2:<ACCT>:parameter/mitjip/prod/*`. With `aws/ssm`, decrypt is allowed through the key's default policy for callers who can call SSM.
- **Delivery:** `deploy.sh` writes each parameter to `/opt/mitjip/secrets/<name>` (`chmod 600`, root, on the EBS root volume, encrypted by default per Q6). Compose maps them as `secrets:`, and FastAPI reads `/run/secrets/*` (pydantic-settings supports a `secrets_dir`). A `chmod 600` `.env` file is the simpler fallback. Never bake secrets into images. Anything `NEXT_PUBLIC_*` is public by design (Next.js inlines it at build, which wasn't verified in this research).
- **DB credentials:** keep the RDS-managed master secret for break-glass/admin only. Create an app role (owner of the schema, used by Alembic) and possibly a restricted runtime role, and store their passwords in Parameter Store. That avoids the app having to follow the master secret's 7-day rotation.
- **GitHub side:** with no secrets in GitHub, the lack of environment secrets on a Free private repo matters little. The lack of **required reviewers and deployment-branch rules** is what you lose. Mitigations are binding the OIDC `sub` to `ref:refs/heads/main`, restricting who can push to `main`, and using `workflow_dispatch` for production deploys. Alternatively, get GitHub Team (free for teachers via GitHub Education, see Q8) or make the repo public.

- KMS customer-managed key pricing wasn't fetched.
- Seoul-region Parameter Store/Secrets Manager prices weren't shown separately (the pages show global/US prices).

## 6. Network: VPC layout, security groups, no-NAT trick, IMDSv2, EBS encryption, Session Manager vs SSH, VPC endpoints

### Takeaway
The proposed layout is right: EC2 in a public subnet with a public IPv4 (~$3.65/month) and RDS in two private subnets (two AZs required) with no route to the internet. **No NAT** (saves ≥ $33/month) and **no interface endpoints** (≈ $7+/month each, ~5 needed). Add the free S3 gateway endpoint. Security groups should allow only 80/443 (plus UDP 443 if Caddy HTTP/3 is wanted) to EC2, 5432 only from the EC2 SG to RDS, and no port 22. Set **IMDSv2-required and EBS encryption-by-default as account/region defaults before launch**. Use Session Manager, including port-forwarding to RDS, instead of SSH.

### Cited Findings
- Public IPv4 costs **$0.005/hour** for both in-use and idle addresses (≈ $3.65/month). NAT gateway costs $0.045/hour plus $0.045/GB (US East Ohio example). **Gateway endpoints have no hourly or data charges.** — [Amazon VPC pricing](https://aws.amazon.com/vpc/pricing/); background on the Feb 2024 IPv4 charge and the old free-tier 750 h: [AWS News Blog: public IPv4 charge](https://aws.amazon.com/blogs/aws/new-aws-public-ipv4-address-charge-public-ip-insights)
- Interface endpoints are billed per hour per AZ (an example shows $0.01/hour per endpoint ENI) plus $0.01/GB for the first PB. — [AWS PrivateLink pricing](https://aws.amazon.com/privatelink/pricing/)
- An RDS subnet group needs subnets in at least two AZs, even for Single-AZ. Set "publicly accessible" to No, use a private route table with only the local route, and allow 5432 from the app security group rather than a CIDR. — [OneUptime: RDS in a private subnet (2026)](https://oneuptime.com/blog/post/2026-02-12-setup-rds-private-subnet/view); [InventiveHQ: Secure RDS access](https://inventivehq.com/knowledge-base/aws/secure-rds-database-access)
- **RDS PostgreSQL 15+ defaults `rds.force_ssl=1`.** libpq clients default to `sslmode=prefer`, so use `sslmode=verify-full` with the RDS CA bundle to prevent spoofing. PG16+ supports TLS 1.3. — [Amazon RDS: Using SSL with PostgreSQL](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Concepts.General.SSL.html)
- IMDS account defaults are per region and apply only to **new** instances: `aws ec2 modify-instance-metadata-defaults --region <r> --http-tokens required`. With the IMDSv2 default, `HttpPutResponseHopLimit` becomes **2**. A separate account-level **enforcement** (`httpTokensEnforced`) blocks launches that aren't IMDSv2. — [EC2 User Guide: IMDS options for new instances](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-IMDS-new-instances.md)
- For existing instances: `aws ec2 modify-instance-metadata-options --http-tokens required --http-endpoint enabled`, and use the `MetadataNoToken` CloudWatch metric to confirm there are no IMDSv1 calls first. The hop limit is adjustable (`--http-put-response-hop-limit`). — [EC2 User Guide: Modify IMDS options for existing instances](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-IMDS-existing-instances.html)
- IMDSv2's PUT response has an IP-level hop limit of **1 by default**, and a bigger limit may be needed "for backward compatibility with container services running on the instance". PUT requests carrying `X-Forwarded-For` are rejected (an SSRF/proxy defense). — [EC2 User Guide: How IMDSv2 works](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-metadata-v2-how-it-works.html)
- EBS encryption-by-default is a **per-region** account setting (`aws ec2 enable-ebs-encryption-by-default --region ap-northeast-2`). It uses `aws/ebs` unless you choose a CMK, has no effect on existing volumes, and can't be disabled per volume once on. — [Amazon EBS: Encryption by default](https://docs.aws.amazon.com/ebs/latest/userguide/encryption-by-default.html)
- Session Manager port forwarding to RDS: `aws ssm start-session --target i-… --document-name AWS-StartPortForwardingSessionToRemoteHost --parameters '{"host":["<rds-endpoint>"],"portNumber":["5432"],"localPortNumber":["5432"]}'` (requires the Session Manager plugin locally). — [AWS SSM: Start a session](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-sessions-start.html)
- Caddy automatic HTTPS needs the A/AAAA records pointing at the server and **port 80 (HTTP-01) or 443 (TLS-ALPN-01) reachable**. A DNS challenge needs no open ports but does need DNS-provider credentials. Caddy redirects HTTP to HTTPS automatically. — [Caddy: Automatic HTTPS](https://caddyserver.com/docs/automatic-https)
- If CloudFront fronts the instance, the SG can allow only `com.amazonaws.global.cloudfront.origin-facing` (managed prefix list). The prefix list carries a "weight" against SG rule quotas. — [CloudFront: managed prefix list](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/LocationsOfEdgeServers.html)

### Inferences
- **Concrete layout:** VPC `10.20.0.0/16`. Public subnets `10.20.0.0/24` (2a, EC2) and `10.20.1.0/24` (2c, spare). Private subnets `10.20.10.0/24` (2a) and `10.20.11.0/24` (2c) for the DB subnet group. The public route table has `0.0.0.0/0 → IGW` plus the S3 gateway endpoint. The private route table has the local route only.
- **SGs:** `sg-app` inbound TCP 80 and 443 from `0.0.0.0/0` (and `::/0` if IPv6), UDP 443 only if you keep Caddy's HTTP/3 (Caddy enables it by default, not verified here), nothing else. Outbound can stay default (it needs ECR, SSM, SES, S3 and OpenAI over 443, plus RDS 5432). `sg-db` inbound TCP 5432 from `sg-app` only, with no outbound needed. Redis stays inside Docker's network with no host port published.
- **Hop limit trade-off:** FastAPI/arq need instance-role credentials (S3 presigned URLs, SES), and from a bridge-network container they need hop limit 2. So keep hop limit 2 (the account default) and make the instance role minimal: S3 on one bucket prefix, `ses:SendEmail` from one identity, ECR read, SSM core, `GetParametersByPath` on `/mitjip/prod/*`. Optionally block `169.254.169.254` for the Caddy and Next.js containers with an iptables `DOCKER-USER` rule so an SSRF in Next.js can't reach the credentials. That rule isn't documented in the sources here, so test it.
- **VPC endpoints aren't worth it.** SSM needs `ssm`, `ssmmessages` and `ec2messages`, and ECR needs `ecr.api` and `ecr.dkr`. That's 5 × ~$7.30 ≈ $36/month for traffic that already leaves through the IGW for free. Endpoints only matter for a private-subnet EC2, which would also need NAT.
- Choose RDS storage encryption at creation (it can't be added later without snapshot/restore; not fetched), and turn on automated backups and deletion protection.

### Gaps
- Seoul-specific NAT and interface-endpoint hourly rates weren't obtained; the figures above are US/global examples.
- Whether the new (post-July-2025) free plan credits cover public IPv4 hours wasn't verified.

## 7. Edge protection: WAF need and cost, Shield Standard, Caddy rate limits and headers (HSTS, CSP), signup/login bot protection, Cloudflare/CloudFront in front

### Takeaway
At a few hundred users, the essentials are app-level Redis rate limits (already planned), **Cloudflare Turnstile** on signup, login, password reset and quote submission (free, works without Cloudflare's proxy), explicit security headers in Caddy, and CSP from Next.js. AWS WAF **can't attach to EC2**. If edge filtering is wanted, the **CloudFront flat-rate Free plan** ($0, includes WAF, IP rate limiting, DDoS, Route 53 DNS and a TLS certificate) is the cheapest AWS-native option, with Cloudflare Free as the non-AWS alternative. Both add origin-lockdown and ACME complexity, so treat them as optional.

### Cited Findings
- WAF protects CloudFront, API Gateway REST, **ALB**, AppSync, Cognito user pools, App Runner, Bedrock AgentCore Gateway, Verified Access and Amplify. EC2 isn't on the list. Web ACLs for CloudFront must be created in us-east-1. — [AWS WAF: Resources you can protect](https://docs.aws.amazon.com/waf/latest/developerguide/how-aws-waf-works-resources.html)
- WAF pay-as-you-go: $5/month per web ACL, $1/month per rule or managed rule group (AWS managed groups aren't free), $0.60 per million requests, Bot Control $10/month plus usage (Common Bot Control includes 10 M requests free), CAPTCHA $0.40 per 1,000 attempts. — [AWS WAF pricing](https://aws.amazon.com/waf/pricing/)
- **CloudFront flat-rate plans (announced Nov 18, 2025):** **Free $0** (1 M requests and 100 GB per month), Pro $15 (10 M and 50 TB), Business $200, Premium $1,000, with no overage charges. WAF-blocked and DDoS requests don't count toward the allowance, the first spike up to 3× is tolerated, and sustained excess may degrade delivery. — [AWS What's New: flat-rate pricing plans](https://aws.amazon.com/about-aws/whats-new/2025/11/aws-flat-rate-pricing-plans); [CloudFront: flat-rate pricing plans](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/flat-rate-pricing-plan.html)
- What the Free plan includes: WAF (AWS threat-intel rules), always-on DDoS, **IP-based rate limiting (5-minute window)**, geo-blocking, header insertion, OAC, signed URLs, Route 53 DNS with DNSSEC, TLS certificate, HTTP/3 and 5 GB of S3 credits. Not included: CAPTCHA and custom WAF responses (Pro+), Bot Control and **VPC origins/origin mTLS (Business+)**. Quotas: **at most 3 Free plans per account**, one apex domain per plan. A web ACL must stay associated, and WAF rule groups, Targeted Bots and ATP/ACFP are unsupported. — [CloudFront: flat-rate pricing plans](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/flat-rate-pricing-plan.html)
- Shield Standard is automatic and free for all AWS customers against common L3/L4 DDoS, with the most comprehensive protection for Route 53, CloudFront and Global Accelerator. — [AWS Shield Standard overview](https://docs.aws.amazon.com/waf/latest/developerguide/ddos-standard-summary.html)
- **Turnstile:** free plan with unlimited challenges (including verification requests), 20 widgets and 10 hostnames per widget. It "can be used independently without requiring other Cloudflare services". — [Cloudflare Turnstile plans](https://developers.cloudflare.com/turnstile/plans/). This conflicts with third-party claims of a 1 M siteverify/month cap: [Piano docs](https://docs.piano.io/en/subscriptions/cloudflare-turnstile), [phpcaptcha review](https://www.phpcaptcha.org/cloudflare-turnstile-review). The official page shows no cap.
- Cloudflare in front: Full (strict) mode needs a valid or Cloudflare Origin CA certificate. Allowlisting Cloudflare IPs at the origin proves only that traffic came via Cloudflare, not via *your* zone, which is why Authenticated Origin Pulls (mTLS) exists. — [Cloudflare: Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict); [Cloudflare IP addresses](https://developers.cloudflare.com/fundamentals/concepts/cloudflare-ip-addresses/); [StackHarbor: allowlisting Cloudflare IPs](https://stackharbor.com/en/knowledge-base/cfops-allowlist-cloudflare-ips-origin-firewall/)
- **Caddy rate limiting isn't in the standard binary.** `mholt/caddy-ratelimit` is a third-party module ("not an official repository"), needs `xcaddy build --with github.com/mholt/caddy-ratelimit`, and its distributed mode is approximate. — [mholt/caddy-ratelimit](https://github.com/mholt/caddy-ratelimit); [StackHarbor: Caddy rate limiting](https://stackharbor.com/en/knowledge-base/caddy-rate-limiting/); [Caddy community: unrecognized directive rate_limit](https://caddy.community/t/unrecognized-directive-rate-limit/30359)
- Caddy's `header` docs show an explicit `Strict-Transport-Security max-age=31536000;`, `X-Content-Type-Options nosniff` and `X-Frame-Options DENY` block ("only use if you understand the implications!"). Neither the header page nor the automatic HTTPS page says HSTS is on by default. — [Caddy: header directive](https://caddyserver.com/docs/caddyfile/directives/header); [Caddy: Automatic HTTPS](https://caddyserver.com/docs/automatic-https)
- **Next.js CSP:** nonce-based CSP is set in `proxy.ts` (Next 16's name for middleware) and **requires dynamic rendering for every page**, which disables static optimization, ISR and PPR. The alternative is a static CSP in `next.config` `headers()` with `'unsafe-inline'`, or the **experimental SRI** hash-based CSP that keeps static generation. — [Next.js: Content Security Policy guide (updated 2026-03-20)](https://nextjs.org/docs/app/guides/content-security-policy)

### Inferences
- **Recommended Caddyfile header block:** `Strict-Transport-Security "max-age=31536000; includeSubDomains"` (add `preload` only after a few stable weeks), `X-Content-Type-Options nosniff`, `Referrer-Policy strict-origin-when-cross-origin`, `Permissions-Policy "camera=(), microphone=(), geolocation=()"` and `-Server`. Leave frame protection to CSP `frame-ancestors 'none'`. Start with the static `next.config` CSP (`'unsafe-inline'` only for styles if possible), and consider the SRI option once it's stable. Nonce CSP would make every page dynamic, which costs CPU on a t4g.small.
- **Bot protection placement:** Turnstile widget on signup, login (always, or after N failures), password reset, vendor registration and quote request. Verify `siteverify` server-side in FastAPI **before** argon2 hashing so bots can't burn CPU. Keep the Redis limits per IP and per account/email.
- **WAF math:** WAF needs an ALB (extra monthly cost, not priced here) or CloudFront. Pay-as-you-go WAF on CloudFront (ACL + ~3 managed groups ≈ $8–9/month plus requests) is now hard to justify next to the $0 Free flat-rate plan. The Free plan's soft 1 M requests/month (~0.4 req/s average) should be enough for tens of concurrent users if static assets are cached at the edge. Watch the 50/80/100% usage emails.
- **CloudFront Free in front of Caddy (optional):** restrict `sg-app` to the CloudFront origin-facing prefix list. Caddy then can't complete HTTP-01/TLS-ALPN from Let's Encrypt, so either use an ACM certificate on CloudFront and send CloudFront → origin over HTTPS with a Caddy DNS-challenge certificate for an `origin.` hostname (needs a Caddy build with a Route 53 DNS plugin), or allow port 80 for ACME only. Forward `Cookie`, `Origin` and `Host` (the session and Origin checks depend on them) and disable caching for `/api/*` and dynamic pages. This is a meaningful amount of work. Do it only if abuse appears, or put it on the post-MVP list.
- **Cloudflare Free alternative:** DNS moves from Route 53 to Cloudflare. Use Full (strict) with an Origin CA certificate in Caddy, allowlist Cloudflare IPs plus Authenticated Origin Pulls, and get free WAF-lite and rate limiting. Turnstile works either way.

### Gaps
- No fetched ALB price for Seoul.
- Whether CloudFront flat-rate plans support custom (EC2) origins without restrictions wasn't stated explicitly. The docs list only "Private origins within VPC" as Business+, which implies public custom origins are fine on Free.

## 8. Supply chain and app security: Dependabot/Renovate, pip-audit, npm audit, Trivy, CodeQL, secret scanning, branch protection; OWASP items for this app

### Takeaway
Pin every action to a full commit SHA (enforce it in repo/org settings) and keep the pins current with Dependabot. Run pip-audit, `npm audit` and Trivy in CI, and lint workflows with zizmor. CodeQL, secret scanning and push protection are **free only on public repos**. On private repos they need paid add-ons that can only be bought on Team/Enterprise. Branch protection and rulesets for private repos also need Pro/Team. The relevant app risks are A01 Broken Access Control (IDOR on quotes and vendor documents), A03 Supply Chain, A07 Authentication, CSRF and session fixation, and the business-registration-certificate upload.

### Cited Findings
- **tj-actions/changed-files (March 2025):** attackers rewrote all version tags up to 45.0.7 to a malicious commit. Users pinned to commit SHAs were largely unaffected. — [Semgrep advisory](https://semgrep.dev/blog/2025/popular-github-action-tj-actionschanged-files-is-compromised)
- **trivy-action / setup-trivy (March 19, 2026):** after an incomplete credential rotation following a late-February intrusion, attackers force-pushed 75–76 of 77 trivy-action tags to code that **stole CI secrets** and then ran the real scan. Malicious Trivy v0.69.4 binaries and Docker Hub images 0.69.5–0.69.6 were also published. Safe versions are trivy-action v0.35.0, setup-trivy v0.2.6 and Trivy ≤ v0.69.3. GitHub's "Immutable" badge didn't prevent the rewrites, and Aqua calls SHA pinning the only reliable protection. Attribution is to TeamPCP, and Barracuda's advisory was still being updated in Aug 2026. — [Aqua: Trivy supply chain attack](https://www.aquasec.com/blog/trivy-supply-chain-attack-what-you-need-to-know); [Barracuda advisory](https://trust.barracuda.com/security/information/trivy-supply-chain-compromise); [Snyk](https://snyk.io/de/articles/trivy-github-actions-supply-chain-compromise/)
- Trail of Bits reports a `pull_request_target` misconfiguration was the entry point exploited in the trivy-action case. zizmor flags template injection, dangerous triggers (`pull_request_target`, `workflow_run`), excessive permissions and unpinned actions. — [Trail of Bits: hardening zizmor (2026-05-22)](https://blog.trailofbits.com/2026/05/22/we-hardened-zizmors-github-actions-static-analyzer/); [Packagist: securing workflows with zizmor](https://blog.packagist.com/securing-our-github-actions-workflows-with-zizmor/); [Grafana: zizmor at scale](https://grafana.com/blog/how-to-detect-vulnerable-github-actions-at-scale-with-zizmor/)
- Since Aug 15, 2025, the GitHub allowed-actions policy can **require full-SHA pinning** (unpinned workflows fail) and block actions with `!`, at enterprise, org and repo level. — [GitHub Changelog 2025-08-15](https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/). `pinact` rewrites tags to SHAs. — [Classmethod: pinact](https://dev.classmethod.jp/en/articles/hardening-github-actions-with-pinact-commit-sha-semver/)
- GitHub hardening guide: default `GITHUB_TOKEN` to read-only, pin to full-length SHAs (and notes that workflow dependency lockfiles, where available, "supersede SHA pinning"), pass untrusted context through `env:` to avoid script injection, avoid `pull_request_target`, use OIDC, keep actions updated with Dependabot, put `.github/workflows` under CODEOWNERS, and don't use self-hosted runners on public repos. — [GitHub Docs: Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)
- Dependabot ecosystems: `github-actions` (version and security updates), `docker` and `docker-compose` (version updates only), `npm`/`pnpm`, `pip` (including PEP 621 `pyproject.toml`) and **`uv`** are supported. Dependabot alerts for actions work only for semver refs, not SHA refs. — [GitHub Docs: Dependabot supported ecosystems](https://docs.github.com/en/code-security/dependabot/ecosystems-supported-by-dependabot/supported-ecosystems-and-repositories); [GitHub Docs: About Dependabot alerts](https://docs.github.com/en/code-security/dependabot/dependabot-alerts/about-dependabot-alerts)
- Renovate is an AGPL-3.0 open-source alternative (self-hosted, or the hosted Mend Renovate App) with schedules and shareable presets. — [Renovate docs](https://docs.renovatebot.com/)

- **CI security stage (all actions SHA-pinned):** `zizmor .github/workflows`; `pip-audit` (or `uv export | pip-audit -r -`); `npm audit --omit=dev --audit-level=high`; `trivy image --scanners vuln,secret --severity HIGH,CRITICAL --exit-code 1 --ignore-unfixed` on the built arm64 image. Use the trivy-action at ≥ v0.35.0 pinned by SHA, or install the binary by checksum. Add a `gitleaks`-style secret scan if the repo is private (no source fetched for gitleaks).
- **Dependabot config:** weekly updates for `github-actions`, `npm` (web), `uv`/`pip` (api), `docker` and `docker-compose`, grouping minor and patch updates. Because Dependabot alerts don't cover SHA-pinned actions, the version-update PRs are what keep the pins fresh. Treat Next.js and React security releases as same-day merges.
- **Public vs private (the decision the team owns):** a public repo gets free 4-vCPU arm runners, CodeQL, secret scanning, push protection, required reviewers and branch protection, but the code and history are public, so secrets must never be committed (push protection helps). A private repo on a Free org gets none of these. To stay private with protections, ask the instructor or teacher to claim **free GitHub Team** through GitHub Education. Branch protection, deployment-branch rules and environment secrets then work, but required reviewers stay public-only and GHAS products remain paid.
- **App-specific checks for 믿집:**
  - (a) IDOR: every quote, request, vendor-document and chat query should be filtered by the session's user or vendor ID or role on the server, never trusted from the path. Add pytest cases where user B requests user A's IDs.
  - (b) Vendor approval and admin elevation are privilege changes. Rotate the session ID or force re-login, and re-check approval status from the DB per request rather than caching it in the session.
  - (c) The planned Origin check plus SameSite=Lax matches OWASP if it rejects a missing Origin on non-GET requests and adds a `Sec-Fetch-Site` check. A JSON-only API with a custom header gives extra margin.
  - (d) 사업자등록증 upload: PDF/JPEG/PNG only, magic-byte check, ≤ 10 MB, random S3 keys under `vendor-docs/<vendor_id>/`, bucket policy blocking public access, short-lived presigned GET (e.g. 5 min) served with `Content-Disposition: attachment`, admin-only access, image re-encode, and PDFs never rendered inline on the main origin.
  - (e) Log auth events (A09) to CloudWatch.

## 9. Infrastructure as code and AWS account hygiene (root MFA, Identity Center, budgets, CloudTrail, GuardDuty)

### Takeaway
A documented console/CLI runbook is acceptable for one EC2 + one RDS. The highest-value IaC targets are the security-critical, easy-to-get-wrong pieces: the OIDC provider and roles, the instance role, security groups, ECR repos and lifecycle, and the SSM document. Put those in a small OpenTofu/Terraform or CloudFormation file. Day-one account hygiene costs almost nothing: root MFA (enforced) or a passkey, no root access keys, Budgets alerts, CloudTrail event history (free) plus one free management-event trail, IMDSv2 and EBS defaults, the GuardDuty 30-day trial, and human access through either an AWS Organization with Identity Center or MFA'd IAM users with `aws login`. Avoid long-lived access keys.

### Cited Findings
- OpenTofu forked from Terraform 1.5.x and reads the same HCL and state (migration is usually one command plus a CI image change). Terraform moved to BSL. CDK is AWS-only and synthesizes CloudFormation. - AWS enforces **MFA for root users across all account types**: management accounts (May 2024), standalone accounts (June 2024 onward), member accounts (June 2025). FIDO2 passkeys are supported, with up to 8 MFA devices per user. — [AWS What's New 2025-06](https://aws.amazon.com/about-aws/whats-new/2025/06/aws-iam-mfa-root-users-across-all-account-types); [AWS Security Blog](https://aws.amazon.com/blogs/security/secure-by-design-aws-enhances-centralized-security-controls-as-mfa-requirements-expand)

### Inferences
- **IaC recommendation:** one `infra/` folder with OpenTofu, or a single CloudFormation template if the team doesn't want state management. It should cover the OIDC provider, `mitjip-gha-deploy` role, EC2 instance role and profile, `sg-app`/`sg-db`, ECR repos with immutability and lifecycle, the `mitjip-deploy` SSM document, the parameter *names* (values set by CLI) and the budget. Create the VPC, EC2, RDS and Route 53 by console following a written runbook, or import them later. This keeps the trust policies and least-privilege JSON reviewable in PRs, which is where mistakes are most costly. If time is short, a README runbook with the exact `aws` CLI commands and JSON files is acceptable.
- **Account checklist (day 1, ap-northeast-2):**
  1. Root: passkey/MFA, no access keys, root email on a team alias, alternate contacts.
  2. Humans: either create an AWS Organization (free) and use an Identity Center organization instance with permission sets (`Admin` for 1–2 leads, `Developer` scoped), or 2–4 IAM users with MFA plus `aws login`. No access keys anywhere.
  3. `enable-ebs-encryption-by-default` and IMDS defaults (`--http-tokens required`), optionally `httpTokensEnforced`.
  4. Budgets at $10 / $30 / $50 with email alerts, plus Cost Anomaly Detection (pricing not fetched).
  5. One CloudTrail trail (management events, all regions) to an S3 bucket with lifecycle expiry after 90–365 days.
  6. GuardDuty on, then review the console's usage estimate before the 30-day trial ends. For one small instance it's likely a few dollars a month (not measured).
  7. S3 Block Public Access at account level.
  8. IAM Access Analyzer (pricing not fetched).
- **Rough monthly security/CI-CD overhead at this scale:** Parameter Store $0; Secrets Manager (RDS master) $0.40; ECR < $1; basic scanning $0; SSM Run Command and Session Manager $0; public IPv4 ≈ $3.65; NAT $0 (avoided, ≥ $33 otherwise); interface endpoints $0 (avoided, ≈ $36 otherwise); CloudFront Free plan $0 (optional); WAF pay-as-you-go $0 unless used; CloudTrail ≈ $0; Budgets $0; GuardDuty a few dollars after the trial (estimate); GitHub Actions $0 (public) or within the $12 Free credit (private).
