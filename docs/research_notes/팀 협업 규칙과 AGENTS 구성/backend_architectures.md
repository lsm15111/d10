# Backend architectures for FastAPI/Python web services — survey for 믿집 (as of 2026-10-29)

Method note (applies to every repo number below): stars/forks were read from each repo's GitHub page (`stargazerCount`), archive status from the GitHub archive banner, and "last commit" from the default branch's `commits.atom` feed, all fetched on 2026-10-29. Directory structures and config snippets come from shallow, tree-only clones (`git clone --depth 1 --filter=blob:none`) read on 2026-10-29. Stars measure attention, not architecture quality. The WebSearch budget ran out midway, so the later sources are known URLs fetched directly. Korean-language coverage is therefore thinner than planned (see Gaps).

## Q1. Which FastAPI/Python repositories and templates are most popular or most praised in 2025–2026? What are their stars, activity and structure?

### Takeaway
The official `fastapi/full-stack-fastapi-template` (46.1k★) and `zhanymkanov/fastapi-best-practices` (18.3k★) are the most-starred structure references. Among real production FastAPI codebases, **Polar's `server/`** (10.4k★, committed today) is the closest analog to 믿집: it uses feature packages with `endpoints/service/repository/schemas/auth/tasks` files, SQLAlchemy async, Alembic, a worker, ADRs and AGENTS.md. Netflix Dispatch is archived (Sep 2025), and several popular "clean/hex" FastAPI examples are stale.

### Inferences
- In the most-starred templates, structure and popularity diverge. The full-stack template's single `models.py`/`crud.py` suits a demo but not 11 feature packages, and Open WebUI (157k★) is flat layer-first. Production repos with many domains (Polar, PostHog, Dispatch, Litestar fullstack) converge on **feature-first packages with fixed per-feature file roles**, which is what 믿집 already does.
- Polar is the best single reference. It has the same stack (FastAPI + SQLAlchemy async + Alembic + Redis worker + generated TS client), the same per-feature file roles, and it is actively developed with written conventions (AGENTS.md, ADRs).

## Q2. How do these projects lay out folders, routers/services/repositories/schemas, DI, settings, errors, background workers, migrations and tests?

### Takeaway
The working default is a feature package with a thin router, a service holding the business logic, and a repository holding every query. Schemas live in the feature package, FastAPI `Depends` handles DI, pydantic-settings handles config, status-coded domain errors are mapped by exception handlers, and one transaction per request or task commits at the boundary. Each feature has a `tasks.py`/`jobs/`, migrations are date-prefixed with a single-head check, and tests mirror the source tree against a real Postgres. DI containers appear only in the clean-architecture showcase repos.

### Cited Findings
**Feature vs layer**
- Feature-first: Polar `polar/{module}/{auth,endpoints,service,repository,schemas,tasks,sorting}.py` ([server/AGENTS.md](https://github.com/polarsource/polar/blob/HEAD/server/AGENTS.md)); zhanymkanov `src/<domain>/{router,schemas,models,service,dependencies,config,constants,exceptions,utils}.py` ([repo](https://github.com/zhanymkanov/fastapi-best-practices)); Dispatch `src/dispatch/<domain>/{models,service,views,flows}.py` ([repo](https://github.com/Netflix/dispatch)); rafsaf `app/<feature>/{views,schemas,models,dependencies}.py + tests/` ([repo](https://github.com/rafsaf/minimal-fastapi-postgres-template)); Litestar fullstack `domain/<area>/…` ([repo](https://github.com/litestar-org/litestar-fullstack)).
- Layer-first: full-stack template ([repo](https://github.com/fastapi/full-stack-fastapi-template)), Open WebUI `routers/ models/` ([repo](https://github.com/open-webui/open-webui)), Mealie `routes/ services/ repos/ schema/` with domain subfolders ([AGENTS.md](https://github.com/mealie-recipes/mealie/blob/HEAD/AGENTS.md)), FastAPI tutorial `routers/` ([docs](https://fastapi.tiangolo.com/tutorial/bigger-applications/)).
- Korean community view: an Inflearn Q&A (2025-02-28) asked "domain folders vs layer folders" for a controller/service/repository FastAPI app. The answers converged on **domain first, layers inside each domain**, with domains drawn by data relationships rather than one folder per model — [Inflearn](https://www.inflearn.com/community/questions/1531846/fastapi-%ED%8F%B4%EB%8D%94-%EA%B5%AC%EC%A1%B0%EC%97%90-%EB%8C%80%ED%95%B4-%EC%A7%88%EB%AC%B8%EC%9D%B4-%EC%9E%88%EC%8A%B5%EB%8B%88%EB%8B%A4). A 2025-05-01 Korean post instead shows layer-first `routers/users.py, schemas/users.py, services/users.py`, thin routers, a separate repository/DAO and `Depends` for sessions/auth — [tilnote](https://tilnote.io/pages/681172fb3c3f2fc7099cbe6c).

**Repository / service rules (Polar's written conventions)**
- "**ALL database queries MUST be in repository files.**" Repositories extend `polar.kit.repository.RepositoryBase` with mixins (soft delete, sorting) and are built via `from_session(session)`. Methods use `self.session` and never take a `session` arg. Auth-scoped reads go through one helper (`select_accessible_org_ids`), enforced by a custom lint task (`lint_org_scope`) — [server/AGENTS.md](https://github.com/polarsource/polar/blob/HEAD/server/AGENTS.md).
- Services are module-level singletons (`resource = ResourceService()`) that take `session` and `auth_subject` as parameters. Read endpoints take `AsyncReadSession` (read replica) and writes take `AsyncSession` — [server/AGENTS.md](https://github.com/polarsource/polar/blob/HEAD/server/AGENTS.md).
- Per-module `auth.py` defines `Annotated[AuthSubject[…], Depends(Authenticator(required_scopes=…, allowed_subjects=…))]` aliases. Endpoints become public by omitting the dependency — [server/AGENTS.md](https://github.com/polarsource/polar/blob/HEAD/server/AGENTS.md).
- Mealie gets repositories via `repos: AllRepositories = Depends(get_repositories)` (a factory), "scoped to group/household context automatically". Schemas use strict suffixes `*In/*Out/*Create/*Update`, and TS types are generated from Pydantic ("never manually edit") — [Mealie AGENTS.md](https://github.com/mealie-recipes/mealie/blob/HEAD/AGENTS.md).
- Polar's schema convention is `ResourceBase` → `Resource` (read, `IDSchema, TimestampedSchema`) / `ResourceCreate` / `ResourceUpdate` ("ALL fields optional with None default") — [server/AGENTS.md](https://github.com/polarsource/polar/blob/HEAD/server/AGENTS.md).

**Transactions / sessions**
- Polar ADR-0003 (2026-07-02), "One request or task is one transaction": application code never calls `session.commit()`. The commit happens in middleware or the worker's session context, with `flush()` for generated IDs and `expire_on_commit=False` — [ADR-0003](https://github.com/polarsource/polar/blob/HEAD/handbook/engineering/decisions/0003-request-scoped-unit-of-work.mdx).
- SQLAlchemy asyncio docs: "A single instance of AsyncSession is not safe for use in multiple, concurrent tasks". Use `async_sessionmaker(…, expire_on_commit=False)` and avoid implicit lazy loads (`selectinload`, `lazy="raise"`, `AsyncAttrs.awaitable_attrs`) — [SQLAlchemy docs](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html).

**Dependency injection**
- FastAPI `Depends` is the DI mechanism in Polar, Mealie, the full-stack template and zhanymkanov. zhanymkanov advises using dependencies for DB-backed request validation and chaining them, and notes they are cached per request — [repo](https://github.com/zhanymkanov/fastapi-best-practices).
- DI-container frameworks showed up only in architecture showcases: dishka in ivan-borovets (`main/ioc/{core,outbound,provider_registry}.py`) and dependency-injector in teamhide (`container.py`). Among the cloned production repos' pyprojects, none listed dishka or dependency-injector (matrix in Q4) — [clean-example](https://github.com/ivan-borovets/fastapi-clean-example), [teamhide](https://github.com/teamhide/fastapi-boilerplate), [dishka](https://github.com/reagento/dishka) (1,298★), [python-dependency-injector](https://github.com/ets-labs/python-dependency-injector) (4,918★, last commit 2026-06-18).
- dishka's FastAPI integration uses `FromDishka[T]`, `@inject`/`DishkaRoute` and `setup_dishka(container, app)` with APP/REQUEST scopes. Plain `Depends` functions still need `@inject` — [dishka docs](https://dishka.readthedocs.io/en/stable/integrations/fastapi.html).
- Litestar declares dependencies at app/router/controller/handler layers with `Provide`. A missing required dependency fails at startup, not at request time — [Litestar DI docs](https://docs.litestar.dev/latest/usage/dependency-injection.html).
- Testing: `app.dependency_overrides[orig] = fake`, reset with `app.dependency_overrides = {}` — [FastAPI docs](https://fastapi.tiangolo.com/advanced/testing-dependencies/).

**Settings**
- FastAPI docs: a `Settings(BaseSettings)` returned by an `@lru_cache` `get_settings()` dependency, so tests can override it. "Don't create a global settings instance" in `config.py` — [FastAPI settings](https://fastapi.tiangolo.com/advanced/settings/).
- pydantic-settings supports `env_prefix`, `env_nested_delimiter="__"`, `.env`, `secrets_dir` (Docker secrets) and `SecretStr`. Priority is init args > env vars > dotenv > secrets — [pydantic-settings docs](https://pydantic.dev/docs/validation/latest/concepts/pydantic_settings/).
- Cosmic Python reads config "through functions, not import-time constants" and keeps it small — [appendix](https://www.cosmicpython.com/book/appendix_project_structure.html). zhanymkanov splits `BaseSettings` per domain — [repo](https://github.com/zhanymkanov/fastapi-best-practices). Dify's rule: "Read configuration through `configs.dify_config`" only — [api/AGENTS.md](https://github.com/langgenius/dify/blob/HEAD/api/AGENTS.md).

**Error handling**
- Polar ADR-0002 (2026-07-02): business errors are `PolarError` subclasses with an explicit `status_code` (404/409/410/403), declared in the endpoint's `responses=` so the generated client gets typed error shapes. **422 is reserved for payload validation**, and the reason given is that default-500 business errors paged on-call through Sentry — [ADR-0002](https://github.com/polarsource/polar/blob/HEAD/handbook/engineering/decisions/0002-status-coded-polar-errors.mdx).
- FastAPI: `@app.exception_handler(MyError)`. Override `RequestValidationError` carefully (str() can leak file/line details), register on Starlette's `HTTPException`, and reuse the default handlers from `fastapi.exception_handlers` — [FastAPI docs](https://fastapi.tiangolo.com/tutorial/handling-errors/).
- Dify: "one application error base per slice with specific subtypes that carry user-facing messages" — [BACKEND_ARCHITECTURE.md](https://github.com/langgenius/dify/blob/HEAD/docs/BACKEND_ARCHITECTURE.md).

**Background workers**
- Polar: each module has `tasks.py` with Dramatiq `@actor(actor_name="resource.created", priority=…)`. A task opens its own `AsyncSessionMaker()` session and commits at the task end, and arguments are excluded from telemetry unless marked `LoggableField` — [server/AGENTS.md](https://github.com/polarsource/polar/blob/HEAD/server/AGENTS.md).
- Litestar fullstack keeps jobs per domain (`domain/accounts/jobs/_oauth_refresh.py`) on SAQ — [repo](https://github.com/litestar-org/litestar-fullstack). benavlabs uses taskiq — [repo](https://github.com/benavlabs/FastAPI-boilerplate). Dify, Saleor, FBA and teamhide use Celery (Q4 matrix). Dify's rule is that retried or redelivered tasks "must keep side effects idempotent" — [api/AGENTS.md](https://github.com/langgenius/dify/blob/HEAD/api/AGENTS.md).
- FastAPI `BackgroundTasks` is for small in-process work. For heavy work, use "a bigger tool like Celery" — [FastAPI docs](https://fastapi.tiangolo.com/tutorial/background-tasks/).
- **arq** (which 믿집 uses): the README says "In maintenance only mode". Issue #510 was opened 2025-10-18 by samuelcolvin: critical security fixes continue, but no new fixes should be expected — [arq](https://github.com/python-arq/arq), [issue #510](https://github.com/python-arq/arq/issues/510). Active alternatives (stars / last commit): Dramatiq 5,335 / 2026-10-27 ([repo](https://github.com/Bogdanp/dramatiq)), SAQ 895 / 2026-10-29 ([repo](https://github.com/tobymao/saq)), taskiq 2,369 / 2026-10-08 ([repo](https://github.com/taskiq-python/taskiq)), procrastinate 1,437 / 2026-10-26 ([repo](https://github.com/procrastinate-org/procrastinate)), Celery 29,098 / 2026-10-28 ([repo](https://github.com/celery/celery)).

**Migrations**
- Polar: `uv run task check_migrations` checks for a "single Alembic head, filename later, column drops are marked". On rebase, the `YYYY-MM-DD-HHMM` filename prefix must be renamed to sort after the target branch's latest migration — [server/AGENTS.md](https://github.com/polarsource/polar/blob/HEAD/server/AGENTS.md).
- zhanymkanov: migrations "static and reversible", with a descriptive slug and a date-prefixed template — [repo](https://github.com/zhanymkanov/fastapi-best-practices). Alembic recommends a `MetaData(naming_convention=…)` (`ix_`, `uq_%(table_name)s_%(column_0_name)s`, `fk_…`, `pk_…`) so autogenerate can drop and alter named constraints — [Alembic docs](https://alembic.sqlalchemy.org/en/latest/naming.html).
- Sentry: schema and code deploy separately. Column/table drops take two steps (`SafeRemoveField` `MOVE_TO_PENDING`, then `DELETE`), large index and backfill work goes in post-deploy migrations, "all statements must complete within 5 seconds", constraints are added `NOT VALID` then validated, and every data migration needs a test — [Sentry develop docs](https://develop.sentry.dev/backend/application-domains/database-migrations/).
- Several apps keep Alembic inside the package: Mealie `mealie/alembic/`, Open WebUI `backend/open_webui/migrations`, Prefect `src/prefect/server/database/`, Dify `api/migrations/`, Litestar fullstack `src/py/app/db/migrations/` (repo trees above).

**Tests**
- Polar: "Test files mirror the source layout: `polar/{module}/endpoints.py` → `tests/{module}/test_endpoints.py`". `test_endpoints`/`test_task` are E2E against the real DB, with class-per-method, one test per scenario and `@pytest.mark.auth` fixtures instead of hand-rolled subjects — [server/AGENTS.md](https://github.com/polarsource/polar/blob/HEAD/server/AGENTS.md). Its DB fixture creates **one Postgres database per xdist worker** (`{db}_{worker_id}`), optionally cloned from a template DB (`POLAR_TEST_DATABASE_TEMPLATE`) — [tests/fixtures/database.py](https://github.com/polarsource/polar/blob/HEAD/server/tests/fixtures/database.py).
- The full-stack template uses a session-scoped fixture that runs `init_db` and deletes rows afterwards, against compose Postgres with `TestClient` — [conftest.py](https://github.com/fastapi/full-stack-fastapi-template/blob/HEAD/backend/tests/conftest.py).
- Cosmic Python splits `tests/{unit,integration,e2e}` so each tier runs separately — [appendix](https://www.cosmicpython.com/book/appendix_project_structure.html). rafsaf co-locates `app/<feature>/tests/` — [repo](https://github.com/rafsaf/minimal-fastapi-postgres-template).
- Kludex's 101 FastAPI tips include #5 "Use HTTPX's `AsyncClient` instead of `TestClient`", #6 "Use Lifespan State instead of `app.state`", #8 a pure ASGI middleware instead of `BaseHTTPMiddleware`, and #10 "Use `pytest.mark.anyio`" — [fastapi-tips](https://github.com/Kludex/fastapi-tips).

### Inferences
- 믿집's `router.py → service.py → repository.py` per feature already matches Polar and zhanymkanov. 믿집's AGENTS.md (read-only) already fixes several rules Polar also has: queries in `repository.py`, one error shape `{"error": {code, message, fields?}}` with IntegrityError → 409, cross-feature calls only through the other feature's service functions, and `client.py` for external APIs (the same file name zhanymkanov uses). The remaining differences from Polar are:
  - (a) **Commit location conflicts with the team rule.** 믿집's AGENTS.md gives `service.py` the commit ("업무 흐름 · 상태 · commit"), and slow work is "a `jobs` row in the same transaction, enqueue after commit". Polar ADR-0003 forbids `session.commit()` in services and commits at the request/task edge. Adopting Polar's rule would require the enqueue to be deferred until after the boundary commit, so this is a team decision (ADR), not a drop-in borrow.
  - (b) Polar ADR-0002 reserves 422 for payload validation and declares error responses via `responses=`, so the generated client sees error shapes. That is additive to 믿집's existing error shape.
  - (c) Tests mirror modules.
  - (d) A single-head migration check (믿집 CI already runs up → down → up and `alembic check`).
- 믿집's migrations use sequential numbers (`0001_baseline.py` … `0004_…`, observed read-only in `backend/migrations/versions/`). Students branching in parallel will hit numbering and multiple-head conflicts. Polar's single-head check plus a date-prefixed rename-on-rebase rule is the cheapest fix.
- 믿집's tests are flat (`backend/tests/test_<feature>.py`, observed). Polar's `tests/<feature>/test_{service,endpoints,tasks}.py` scales better once quote/visit/schedule land. Per-xdist-worker databases are the proven way to parallelise real-Postgres tests without testcontainers.
- Polar's central `models/` package is a deliberate counter-pattern to per-feature `models.py`. It sidesteps ORM relationship import cycles (PostHog solves the same with string app labels). If 믿집's import-linter layers start fighting SQLAlchemy relationships across `account|project|vendor`, a shared models package or string-based `relationship("Vendor")` is the known escape hatch.
- Read-replica sessions (`AsyncReadSession`) and singleton service instances are Polar-scale details and are not needed for 믿집.

### Gaps
- I did not read Polar's `enqueue_job` implementation, so I can't confirm whether jobs are buffered until commit (an outbox-like guarantee). That would need code reading.
- pytest's "good practices" page (test layout and import mode) returned HTTP 429 twice and was not used.

## Q3. Which architectural styles (modular monolith with import-linter, hexagonal, clean architecture, vertical slices, Cosmic Python DDD-lite) pay off for small teams, according to real projects?

### Takeaway
The best-evidenced style at every scale is the **modular monolith with mechanically enforced import direction**. Kraken (≈28k modules, ≈400 devs) uses import-linter layers plus independence, Dify uses import-linter layers with a shrinking baseline, and PostHog uses facades enforced by import-linter and tach. Hexagonal/clean/DDD layouts appear mainly in showcase repos with few stars or stale activity. Their own authors (Cosmic Python, Bogard) say they pay off only when domain complexity, not CRUD, dominates.

### Cited Findings
**Modular monolith + import contracts**
- Kraken: 27,637 modules, ~400 developers, one approval to merge. Top-level layers are `kraken.clients → kraken.territories → kraken.core`, with independence contracts between clients and between territories and 40+ contracts in total, run on every PR. Existing violations were exempted with `ignore_imports` and tracked as a debt burndown from 1 May 2022, with 15 left at writing. Drawbacks: breaking layers requires inversion of control, and code piles up in the easier-to-change upper layers. Lesson: apply layering early, because retrofitting is costly. Source: EuroPython blog, 11 Jul 2023 (older but primary) — [EuroPython blog](https://blog.europython.eu/kraken-technologies-how-we-organize-our-very-large-pythonmonolith/).
- Kraken 2026: still "a monolithic Django application in a single git repository", ~15M lines, 2,000+ ORM models and 100k+ tests per merge. That post does not mention import-linter — [Kraken engineering, 2026-03-09](https://engineering.kraken.tech/news/2026/03/09/how-we-ship-2026.html). Kraken's 2024 linting post confirms import-linter "enforces the application's layering", alongside mypy, Ruff and Fixit custom linters run only on changed files — [Kraken engineering, 2024-01-05](https://engineering.kraken.tech/news/2024/01/05/linting-and-formatting.html).
- Dify (`api/.importlinter`): `layers = controllers, services, core, libs`. The comment reads "Migration baseline: keep every exception exact", with `unmatched_ignore_imports_alerting = error` "so this list shrinks whenever a legacy dependency is removed" — [api/.importlinter](https://github.com/langgenius/dify/blob/HEAD/api/.importlinter). Dify's architecture doc: "Treat a boundary violation as a design problem to fix, not an exception to record" — [BACKEND_ARCHITECTURE.md](https://github.com/langgenius/dify/blob/HEAD/docs/BACKEND_ARCHITECTURE.md).
- PostHog: "Each product … is a **vertical slice**". The facade (`facade/api.py` + `contracts.py` frozen dataclasses) is the only cross-product interface. Import-linter contracts include `"presentation must use facade"` (forbid all `products.*.backend`, then allowlist facade/presentation) and `"routes must only import presentation"`, each with a long TODO ignore list — [pyproject.toml](https://github.com/PostHog/posthog/blob/HEAD/pyproject.toml), [products/README.md](https://github.com/PostHog/posthog/blob/HEAD/products/README.md). PostHog's motivation is selective CI testing (Turbo + tach), and it warns that "No importers" is necessary, not sufficient, because in-process HTTP tests, `apps.get_model` and migrations couple code with zero imports — [products/architecture.md](https://github.com/PostHog/posthog/blob/HEAD/products/architecture.md).
- PostHog lets products plug behaviour into core only via approved base classes (QueryRunner, MaxTool, Temporal workflows) in designated locations, with `issubclass` validation at registration ("Import linters … see only the import graph") — [products/architecture.md](https://github.com/PostHog/posthog/blob/HEAD/products/architecture.md).
- Shopify (Ruby, cross-language evidence), 2019: chose a modular monolith over microservices and reorganised from models/views/controllers into domains (orders, shipping, billing). Its Wedge tool scored component isolation in CI — [Shopify Engineering 2019](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity). In 2024, Packwerk 3.0 **removed privacy checks** because they turned it into "an API design tool". Lessons: "enforcing boundaries doesn't design them", static checks miss autoload/routes/fixtures, "running code is the best measure of progress", and domain components did not match how code runs — [A Packwerk Retrospective, 2024-02-07](https://shopify.engineering/a-packwerk-retrospective).
- Boundary choice: Milan Jovanović (2026-06-20) says "Let consistency draw your boundaries". Start with fewer, coarser modules, since splitting later is cheap and merging is expensive. Warning signs are frequent cross-module reads and sync-only event handlers — [blog](https://milanjovanovic.tech/blog/the-modular-monolith-boundary-i-couldnt-take-back). Kamil Grzybek (2019) defines a modular monolith as one deployment unit with independent business modules that have well-defined contracts and encapsulation — [primer](https://www.kamilgrzybek.com/blog/posts/modular-monolith-primer). Fowler (2015): MonolithFirst, "design a monolith carefully" with modular API and data boundaries — [bliki](https://martinfowler.com/bliki/MonolithFirst.html).

**Hexagonal / clean / DDD / vertical slices**
- Hexagonal intent: the app is "driven equally by users, programs, automated tests"; primary (driving) vs secondary (driven) ports; testability without a DB — [Cockburn](https://alistair.cockburn.us/hexagonal-architecture/). Clean Architecture (2012): "source code dependencies can only point inwards" — [Uncle Bob](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html).
- Vertical slices (Bogard, 2018): organise by request, and layered designs lead to mock-heavy tests and forced service/repository layers. The caveat is that it assumes the team can recognise code smells and refactor — [jimmybogard.com](https://www.jimmybogard.com/vertical-slice-architecture/).
- Cosmic Python on repositories: if the app is a CRUD wrapper you "don't need a domain model or a repository". The pattern pays off "sometimes", as complexity grows, and every layer of indirection adds a learning curve — [ch. 2](https://www.cosmicpython.com/book/chapter_02_repository.html). Incremental adoption: "start with a service layer", add a message bus once use cases call each other, and treat the patterns as tools, not "ascetic discipline" — [epilogue](https://www.cosmicpython.com/book/epilogue_1_how_to_get_there_from_here.html).
- Dify **is** moving to ports-and-adapters, but incrementally and only "where business complexity warrants": transport → application services → pure domain (no I/O: no queries, sessions, enqueueing or email) → infrastructure → a single composition root. Domain code goes in `api/domain/<area>/`, use cases in `api/services/` and adapters in `api/repositories/` — [BACKEND_ARCHITECTURE.md](https://github.com/langgenius/dify/blob/HEAD/docs/BACKEND_ARCHITECTURE.md).
- Showcase-level evidence: ivan-borovets (597★) enforces `(main) → inbound → outbound → core` plus CQRS forbidden contracts (commands ↛ queries) — [pyproject](https://github.com/ivan-borovets/fastapi-clean-example/blob/HEAD/pyproject.toml). teamhide (1,496★, last commit 2025-06) nests a user feature five levels deep (`adapter/input/api/v1/request`) — [repo](https://github.com/teamhide/fastapi-boilerplate). The older hex examples are stale (GArmane 2020, pgorecki 2025-01) — [GArmane](https://github.com/GArmane/python-fastapi-hex-todo), [pgorecki](https://github.com/pgorecki/python-ddd).

### Inferences
- For a 4–6 person student team, the evidence favours what 믿집 already trialled: a feature-package modular monolith with an import-linter **layers** contract, plus **independence** contracts between sibling features (Kraken's two contract types). Full hexagonal/clean layering per feature (teamhide/ivan-borovets) multiplies files without a matching payoff for CRUD-heavy features like account/vendor/files.
- 믿집's pure calc engine is the one place where Dify-style domain purity (no I/O, no session, no enqueue) clearly pays off. Making `calc` a bottom-layer package that imports nothing app-specific matches Dify's "domain layer" rule and Cockburn's testability motivation.
- Kraken's and Dify's baseline handling (`ignore_imports` with `unmatched_ignore_imports_alerting = error` and a tracked count) is directly copyable. It turns layer violations into a visible, shrinking number instead of a blocked merge.
- Shopify's retrospective warns that import contracts verify a graph but don't design it. The 흐름 layer (schedule → visit → quote) is the one most likely to be mis-drawn. Milan Jovanović's "consistency draws boundaries" suggests quote/visit/schedule should stay one module if they need same-transaction consistency.
- PostHog's facade idea (cross-feature calls only through a small public module) is worth borrowing at one level, e.g. `vendor/api.py` used by quote. Its frozen-dataclass contracts, Turbo selective testing and tach-plus-import-linter duplication are beyond what a bootcamp team needs.

### Gaps
- I found no PyCon US 2025/2026 or PyCon KR 2024–2026 talk specifically on Python modular monoliths. The searches returned mostly non-Python talks before the budget ran out. The closest Korean conference item is PyCon KR 2023 "FastAPI Deep Dive" (2023-08-12), which is about FastAPI internals and speed, not app structure — [pyvideo](https://pyvideo.org/pycon-korea-2023/fastapi-deep-dive.html). PyCon India 2025's "Is FastAPI really fast?" is about benchmarks — [PyCon India](https://cfp.in.pycon.org/2025/talk/GGV3EJ/).
- No controlled evidence (metrics) compares small-team productivity across styles. The evidence is practitioner reports.

## Q5. How do these projects document their architecture (ARCHITECTURE.md, C4, ADRs, module READMEs, AGENTS.md)?

### Takeaway
In 2026 the dominant pattern in active Python backends is **nested AGENTS.md files plus a small set of architecture or decision docs**, not a matklad-style root ARCHITECTURE.md. None of the 21 cloned repos has a root ARCHITECTURE.md. - Dify's `api/AGENTS.md` sends agents to `docs/BACKEND_ARCHITECTURE.md`, `BACKEND_REPOSITORIES.md`, `BACKEND_SQLALCHEMY.md`, `BACKEND_DATABASE_SCHEMA.md` and `controllers/API_SCHEMA_GUIDE.md`, and backs the rules with checks (an ast-grep guard rejects new `Base` subclasses) — [api/AGENTS.md](https://github.com/langgenius/dify/blob/HEAD/api/AGENTS.md).
- Polar: `handbook/engineering/decisions/` holds 16 ADR files, starting with `0001-record-architecture-decisions` and including `0002-status-coded-polar-errors`, `0003-request-scoped-unit-of-work` and `0005-auth-subject-and-scopes`, each with Status/Area/Date + Context/Decision/Consequences/Alternatives. There is also an `.agents/skills/adr-check` skill — [ADR-0002](https://github.com/polarsource/polar/blob/HEAD/handbook/engineering/decisions/0002-status-coded-polar-errors.mdx), [ADR-0003](https://github.com/polarsource/polar/blob/HEAD/handbook/engineering/decisions/0003-request-scoped-unit-of-work.mdx).
- The ADR format (Nygard, 2011) has a numbered title, Context, Decision ("We will…"), Status (proposed/accepted/deprecated/superseded) and Consequences. Records are stored in-repo (`doc/arch/adr-NNN.md`), never reused, and superseded rather than deleted — [Cognitect](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions).
- C4 has four levels (system context, container, component, code) plus landscape, dynamic and deployment diagrams — [c4model.com](https://c4model.com/).
- Import-linter configs double as documentation: Dify's contract is named "Backend modules follow the transport, application, execution-kernel, and shared-library layers" with commented exceptions, and PostHog comments each ignore with a TODO ("move them into presentation/ and drop the line") — [Dify](https://github.com/langgenius/dify/blob/HEAD/api/.importlinter), [PostHog](https://github.com/PostHog/posthog/blob/HEAD/pyproject.toml).
- Kraken keeps linters in the codebase so "their history and reasoning can be traced back to the pull requests that introduced them" — [Kraken engineering](https://engineering.kraken.tech/news/2024/01/05/linting-and-formatting.html).

### Inferences
- 믿집 already follows most of this pattern (observed read-only). It has a root `AGENTS.md` (with `CLAUDE.md` → `@AGENTS.md`) holding rules plus a layer diagram and invariants (`calc` is pure, the one allowed lazy import), `docs/design/*.md` for rationale, numbered ADRs in `docs/adr/` (0001-stack, 0002-vendor-written-quotes, 0003-openai-rds) with ADRs ranked above AGENTS.md, and `docs/status.md` for progress. That is effectively the backend.ai rules/background split. The evidence supports three remaining additions:
  - (1) A nested `backend/AGENTS.md` only if the root file grows past what agents can hold. Polar, Dify and Prefect nest per subproject.
  - (2) Promoting the open D/R/S/K decisions that are hard to reverse into `docs/adr/` as they close, following Polar's Status/Date/Context/Decision/Consequences/Alternatives template.
  - (3) Writing the layer diagram into import-linter contract names, comments and Korean `broken_contract_guidance`, so the documented invariant is also the enforced one.
- backend.ai's "rules in AGENTS.md, background elsewhere, state each rule once at its highest scope" convention, written partly in Korean, is the closest model for a Korean student team's multi-file docs.
- For a bootcamp presentation, C4 context and container diagrams are enough. Component-level C4 would duplicate the import-linter layer list.

- I could not fetch the C4 site's guidance on how many diagram levels teams usually need (the fetched page didn't state it).
- I didn't sample PostHog's 64 AGENTS.md files for content patterns.

## Q6. Ranked recommendation for 믿집: which repo or template to borrow from, what to borrow, and what not to copy

### Takeaway
Use **Polar's server conventions** as the primary model. Layer on **zhanymkanov's checklist**, **Dify's and Kraken's import-linter baseline practice**, and **PostHog's facade idea at one level**. Take the client-generation and compose setup from the official template. Treat Cosmic Python, the clean/hex repos and Open WebUI as things to learn from, not copy.

### Cited Findings
(Supporting evidence for each rank is cited in Q1–Q5. Ranks 1–12 are recommended to borrow from, ordered by fit; ranks 13–16 are listed as references or explicit "don't copy" cases. The ranking itself is an inference.)

1. **polarsource/polar `server/`** — [repo](https://github.com/polarsource/polar)
   - *Borrow:* the per-feature file roles, including `auth.py` holding `Annotated` authenticator aliases and `tasks.py` per feature. Also: a `RepositoryBase` + `from_session` (믿집 already keeps queries in repositories); ADR-0002 (status-coded domain errors, 422 reserved, `responses=` so the openapi-typescript output includes error shapes); tests mirroring modules with per-xdist-worker DBs; `check_migrations` (single head) with date-prefixed migration names; the ADR template fields. *Decide by ADR, don't drop in:* ADR-0003 (no commit in services) conflicts with 믿집's AGENTS.md rule that `service.py` commits and enqueues the `jobs` row after commit.
   - *Don't copy:* read-replica `AsyncReadSession`, the ~90-module scale, the central 114-file `models/` (only if relationship cycles force it), Dramatiq (sync-first; 믿집's plan is arq→SAQ per its own design doc), backoffice/Stripe specifics.
2. **zhanymkanov/fastapi-best-practices** — [repo](https://github.com/zhanymkanov/fastapi-best-practices)
   - *Borrow:* per-domain `exceptions.py`/`constants.py`/`dependencies.py`; module-aliased cross imports; DB naming (`_at`/`_date`, singular snake tables, explicit index/constraint naming); dependencies as DB-backed validators; async client tests and `dependency_overrides`; ruff.
   - *Don't copy:* `requirements/*.txt` (uv already covers this); per-module `BaseSettings` everywhere (fine, but Dify's single config owner may be simpler for a student team).
3. **langgenius/dify `api/`** — [repo](https://github.com/langgenius/dify)
   - *Borrow:* an import-linter `layers` contract with an exact, commented baseline and `unmatched_ignore_imports_alerting = error` (the baseline can only shrink); the "boundary violation = design problem" rule; domain-purity rules for 믿집's `calc` (no I/O, sessions, enqueueing or LLM calls); idempotent retried tasks; a BACKEND_ARCHITECTURE.md-style doc linked from AGENTS.md.
   - *Don't copy:* full ports-and-adapters with consumer-owned ports per slice, Flask/Celery specifics, its doc volume.
4. **Kraken (EuroPython 2023 + engineering blog)** — [post](https://blog.europython.eu/kraken-technologies-how-we-organize-our-very-large-pythonmonolith/)
   - *Borrow:* the two contract types (layers for the stack, **independence** between siblings such as `account|project|vendor` and `files|refprice|jobs`); `ignore_imports` count tracked as a debt metric; "apply layering early"; linters on changed files only.
   - *Don't copy:* 40+ contracts, Fixit custom linters.
5. **PostHog/posthog `products/`** — [README](https://github.com/PostHog/posthog/blob/HEAD/products/README.md)
   - *Borrow:* the enforcement half of the facade idea. 믿집's AGENTS.md already makes the other feature's `service` public functions the cross-feature interface, so the useful part is PostHog's allowlist-style `forbidden` contract ("forbid all of `products.*.backend`, allow facade") applied as "other features may import `<feature>.service`/`schemas` but not `repository`/`router`", with the one documented `auth.service → vendor.repository` exception as an `ignore_imports` entry. Also the "wiring" rule: plug-ins such as LLM tools register via an approved base class, validated at registration. This is relevant to `agent` tool registries.
   - *Don't copy:* frozen-dataclass contracts everywhere, Turbo selective testing, running tach and import-linter together, product-level MCP/skills.
6. **fastapi/full-stack-fastapi-template** — [repo](https://github.com/fastapi/full-stack-fastapi-template)
   - *Borrow:* `generate_unique_id_function` (stable, readable operationIds help openapi-typescript output too), `compose watch` + override file, mypy+ty in CI, pre-commit. 믿집 already generates types with openapi-typescript (`pnpm gen:api` → `schema.d.ts`, as Polar does), so the template's hey-api `openapi-ts.config.ts` is an alternative to know about, not a needed change.
   - *Don't copy:* layer-first single `models.py`/`crud.py`, SQLModel, sync `Session`, delete-all-rows test fixture.
7. **Cosmic Python (book + code)** — [book](https://www.cosmicpython.com/book/epilogue_1_how_to_get_there_from_here.html), [code](https://github.com/cosmicpython/code)
   - *Borrow:* the service layer as the first investment; unit/integration/e2e test tiers; config read via functions; fake repositories only where unit tests need them (calc and agents).
   - *Don't copy:* classical-mapped domain models separate from the ORM for CRUD features, the message bus, Redis pub/sub as messaging.
8. **mealie-recipes/mealie** — [AGENTS.md](https://github.com/mealie-recipes/mealie/blob/HEAD/AGENTS.md)
   - *Borrow:* the schema suffix convention (`*Create/*Update/*Out`); "generated TS types: never edit"; one AGENTS.md describing backend + frontend contracts.
   - *Don't copy:* the layer-first top-level split, class-based controller mixins.
9. **litestar-org/litestar-fullstack** — [repo](https://github.com/litestar-org/litestar-fullstack)
   - *Borrow:* per-domain `jobs/` and `listeners.py` placement, and a SAQ reference integration if the arq exit condition triggers.
   - *Don't copy:* Litestar-specific controllers, guards and advanced-alchemy.
10. **lablup/backend.ai** — [AGENTS.md](https://github.com/lablup/backend.ai/blob/HEAD/AGENTS.md)
    - *Borrow:* the AGENTS.md (rules) / KNOWLEDGE.md (background) / README (humans) split; "a rule only once at the highest scope"; Korean writing rules using code names for layers; a proposals (BEP) folder for design decisions.
    - *Don't copy:* the Pants build system, the 42-file AGENTS.md sprawl.
11. **ivan-borovets/fastapi-clean-example** — [pyproject](https://github.com/ivan-borovets/fastapi-clean-example/blob/HEAD/pyproject.toml)
    - *Borrow:* examples of import-linter syntax (optional `(main)` layer, `containers`, forbidden contracts such as commands ↛ queries), and ruff's banned-API message style.
    - *Don't copy:* the inbound/outbound/core split, the dishka container.
12. **rafsaf/minimal-fastapi-postgres-template** — [repo](https://github.com/rafsaf/minimal-fastapi-postgres-template)
    - *Borrow:* nothing structural. It is a reference for a tiny, current (2026 v7) async SQLAlchemy + asyncpg setup with co-located tests, if the team prefers `app/<feature>/tests/`.
13. **Netflix/dispatch** (archived) — [repo](https://github.com/Netflix/dispatch): *Borrow* the idea of a `flows.py` orchestration module per domain (a cousin of 믿집's 흐름 layer). *Don't* depend on it or copy it, since it is archived and read-only.

The second is plugin-heavy, uses Celery and requirements.txt, and puts `api/crud/model/schema/service` inside each app — [teamhide](https://github.com/teamhide/fastapi-boilerplate), [FBA](https://github.com/fastapi-practices/fastapi_best_architecture).
